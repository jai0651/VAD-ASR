Decision Log

Every significant choice, ADR-style: the context, the alternatives, why, and what production does instead. Includes the failures and the measurements — decisions without evidence are just opinions.

D1From-scratch models are the default; production engines are config-switchable

Context: the repo's purpose is learning, but the original question was "is this how production looks?" — which requires having the production stack to compare against.

Decision: every pipeline slot defaults to the model built in this repo (VOICE_*_ENGINE=scratch); Silero/faster-whisper/Kokoro are one env var away, framed explicitly as "in production, use this instead".

Alternatives: pretrained-only (fast but you learn glue, not speech); scratch-only (no calibration against reality).

Why: the A/B on identical mic audio is the curriculum — the quality gap you hear is the data/architecture content of docs 2–4 made audible.

D2Endpointing is a separate layer from VAD

Decision: VAD emits per-window P(speech); a pure-logic state machine (endpointing.py) owns turn detection: debounce, hysteresis, pre-roll, silence timeout, min/max utterance bounds.

Alternatives: Silero's bundled utterance iterator (hides the policy — the opposite of instructive); thresholding VAD directly in the orchestrator (untestable, untunable).

Why: the policy layer is where every real deployment tunes UX (end_silence_ms is the single most user-visible number in the system), and pure logic means the entire behavior is unit-tested without models (tests/test_endpointing.py).

Production counterpart: identical structure; the frontier replaces the fixed silence timeout with semantic turn detection.

D3Utterance-based ASR (transcribe on endpoint), not streaming partials

Decision: ASR runs once per closed turn on the full utterance.

Alternatives: chunked pseudo-streaming Whisper (complex, hacky context management); RNN-T for true streaming (a different, bigger model family).

Why: at RTF 0.08 the whole turn transcribes inside the endpoint wait that exists anyway; this is also what most open production agents (pipecat/LiveKit examples) ship. Streaming partials are documented as the extension (docs 3.4), needed for live captions and semantic endpointing.

D4Barge-in via task cancellation + client-side buffer flush

Decision: the whole reply (ASR→respond→TTS) is one asyncio task; confirmed speech during THINKING/SPEAKING cancels it and sends interrupted so the client drops queued audio.

Why one task: cancellation semantics come for free and cleanup is structural. Why the client flush matters: cancelling the producer doesn't empty the consumer's buffer — without the flush the agent audibly "keeps talking" after being interrupted.

Consequence accepted: a sentence already inside a worker thread finishes computing (wasted compute, bounded by one sentence) — Python threads can't be safely killed mid-kernel.

D5ASR/TTS in worker threads; VAD inline on the event loop

Decision: blocking model calls go through asyncio.to_thread; VAD (<1 ms/window) runs inline.

Why: the receive loop must keep draining mic frames during a 300 ms+ transcription or barge-in is physically impossible (the agent is deaf while busy). Threads suffice because PyTorch/CTranslate2 release the GIL inside kernels.

Production counterpart: the same seam, scaled: threads → bounded worker pools → RPC to batching GPU services (docs 5.4).

D6Wire protocol: raw PCM16 binary frames + JSON text events over one WebSocket

Alternatives: WebRTC (production-grade transport with AEC/jitter handling, but an order of magnitude more moving parts); Opus encoding (bandwidth win, irrelevant on localhost); base64-in-JSON (33% overhead for nothing — though notably it's what telephony media-stream APIs do for compatibility).

Why: binary/text frame separation is idiomatic WebSocket, trivially debuggable, and structurally identical to commercial realtime voice APIs — the learning transfers.

D7Engines are structural interfaces; weights shared per process, state per session

Decision: push / transcribe / synthesize / respond duck-typed interfaces; ASR/TTS constructed once in the lifespan hook, VAD+endpointer+orchestrator per connection.

Why: (a) conversation policy becomes unit-testable with fakes — the barge-in test runs in milliseconds with zero downloads; (b) "weights are shared, state is not" is the serving invariant worth internalizing; (c) the interface seam is where RPC goes when scaling out.

D8TTS is a per-sentence generator everywhere

Decision: synthesize(text) yields audio sentence by sentence in both engines.

Why: time-to-first-audio ≈ sentence one (measured: Kokoro ~1.1 s for sentence 1 of a 5.3 s reply); barge-in wastes at most one sentence; and it composes with a future streaming LLM (cut at first sentence boundary). Latency by pipelining, not by faster models.

D9The "brain" is a Responder protocol; echo default, Claude one env var away

Why echo default: the repo teaches speech, not prompting; echo closes the loop with zero API keys and keeps every test hermetic.

The LLM swap, implemented: VOICE_RESPONDER=claude activates ClaudeResponder — a real conversational brain with per-session history (which is why responders are built per connection, like VADs: history is state, and state is never shared between users). Barge-in composes for free: the reply task that gets cancelled now simply contains an LLM call.

Production nuance recorded, not implemented: we make one blocking LLM call per turn. Real agents stream tokens and cut at the first sentence boundary so TTS starts while the LLM is still writing — LLM time-to-first-token dominates the reply budget, and that overlap wins back several hundred ms.

D10TTS from scratch = Tacotron-mini + Griffin-Lim, single speaker, deliberately overfit

Alternatives considered: FastSpeech-style (needs external alignments — a second dependency to teach); VITS-style end-to-end (adversarial training, too heavy for a laptop CPU and too entangled to dissect); concatenative/formant synthesis (instructive DSP but a dead end pedagogically).

Why Tacotron: it exposes the three concepts the whole field is built on (attention-decides-durations, stop tokens, the mel↔waveform seam), trains to intelligibility on one speaker's ~2 minutes in ~20 CPU-minutes, and its failure modes are the exact motivations for FastSpeech/VITS/Kokoro (docs 4.6).

Why Griffin-Lim: zero-training inverse of Module 0 — the only vocoder whose every line you can derive. The audible robotic residue is the lesson.

D11Guided attention penalty added after measured failure

Evidence: attempt 1 (no prior, 3000 steps): mel L1 0.81→0.24 yet free-running attention smeared; generation stopped at 2.2 s on an 82-char sentence; Whisper-as-judge CER ≈ 0.4–1.0 across seen sentences.

Decision: add DC-TTS guided attention (W[t,n]=1−exp(−(n/N−t/T)²/2g²), weight 5.0) + stop-head guards (2 consecutive votes, ~5 frames/char minimum) at inference.

Lesson recorded: for seq2seq TTS, the loss curve is not the health metric — the alignment map is; and keep an end-to-end judge (transcribe your own TTS with a strong ASR).

D11bDecode-time attention windowing: tried, measured, rejected

Context: free-running attention sometimes stalls on a character (exposure bias), so we tried the classic deployed-Tacotron hack: hard-mask attention to a window around its current position, with forced advance on stall.

Evidence: ASR-judge CER got worse (best sentence 0.22 → 0.44; a stall-rescue variant collapsed several sentences to unintelligible 10 s runs). Cause: the model was trained with full-softmax attention; a renormalized window produces context vectors from a distribution it never saw.

Decision: keep decoding faithful to training (stop-head guards only); attack exposure bias where it lives — training data, scheduled sampling, or non-autoregressive architectures.

Lesson recorded: measure your "obvious fix" against a judge before shipping it; inference-time hacks that change the input distribution can subtract value.

D11cCheckpoint selection by ASR judge, not by loss or recency

Decision: every 1000 steps the training script synthesizes 4 seen sentences, transcribes them with whisper, and promotes the checkpoint to tts.pt only if mean CER improved (tts_last.pt keeps the latest).

Why: free-running intelligibility oscillates between checkpoints while teacher-forced loss stays flat — the loss can't see exposure bias. Selecting on an end-to-end judged metric is standard production practice (same idea as picking LLM checkpoints by eval win-rate, not perplexity).

Evidence (final 10k-step run, 29 utterances): judge CER by step: 1000→0.96, 2000→0.80, 3000→1.01, 4000→0.75, 6000→0.63, 7000→0.78, 8000→0.61 (kept), 9000→0.73, 10000→0.66. Three regressions after new bests — "take the last checkpoint" would have shipped 0.66 instead of 0.61, and a shorter run without selection could have shipped 1.01.

D12TTS training runs on CPU by default, not MPS

Evidence: measured 0.24 it/s on Apple MPS vs 3.2–4.6 it/s on CPU — CPU ~13× faster for this model.

Why: the decoder is a Python loop of tiny matmuls; every op pays GPU dispatch overhead that dwarfs the math. GPUs win on large parallel batches, not long sequential chains of small ops. (The batched conv/GRU training of Modules 1–2 does benefit from MPS — the difference between the two cases is the lesson.)

D13E2E test pads with mic-like noise, not digital zeros

Evidence: scratch VAD on exact zeros: mean P(speech)=0.335, flickering (the training generator always had a noise floor → zeros are out-of-distribution); on σ=0.005 noise: 0.004, rock-solid.

Decision: the test simulates reality (mics always have a noise floor) rather than retraining the model for an input real serving never produces.

Lesson recorded: train/serve skew fails silently; keep input-hygiene tests (docs 2.5).

D14Whisper's own VAD filter and text-conditioning are OFF

Why: our endpointer already trims silence — a second VAD adds latency and a second opinion to debug; condition_on_previous_text=False because utterances are independent turns and conditioning compounds hallucinations across turns. General principle: when you own a pipeline stage, disable the model's internal duplicate.

D15Metrics: in-process rolling p50/p95 per stage, JSON endpoint

Alternatives: full Prometheus + Grafana (right for prod, noise for learning); nothing (flying blind).

Why: the decomposition (asr_ms, tts_sentence_ms, turnaround_ms, barge_ins, discards) is the part that transfers; percentiles-not-averages is the habit worth forming. Bounded deques so memory can't creep.

D16uv + pydantic-settings + pytest as the engineering baseline

Why: locked reproducible env (uv.lock), every tunable in one typed object overridable by VOICE_* env vars (no constants buried in model files), and the policy layers covered by fast hermetic tests. Minimal, but it's the skeleton production code hangs on.
