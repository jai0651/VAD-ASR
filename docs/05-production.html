Production Inference

What separates "my model works" from "my service works": loading, latency, concurrency, observability, scale — grounded in what this repo implements and honest about what it skips.

5.1The mental shift

Research asks "is the output good?". Serving asks five different questions: how fast (p95, not average) · how many at once · what breaks and who notices · how much per request · how do I change it safely. Every section below is one of these questions applied to speech.

5.2Model lifecycle

  • Load once, share, never per-request — weights are immutable so they're safe to share across sessions; loading is seconds and hundreds of MB. In server/app.py this is the FastAPI lifespan hook. The rule's other half: per-session state (VAD RNN state, endpointer, conversation) is never shared.
  • Readiness ≠ liveness — /healthz returns 503 until models are loaded, so a load balancer doesn't route to a replica still downloading weights. In Kubernetes terms: that's the readiness probe; liveness would be "the process responds at all".
  • Weights are artifacts, not code — checkpoints download at first run to a cache (models/), pinned by name/version. Production adds checksums and a model registry; the shape is the same.

5.3Latency engineering

  • Measure percentiles per stage. /metrics reports p50/p95 for asr_ms, tts_sentence_ms, and turnaround_ms. Never averages: latency is long-tailed and the tail is what users feel. The stage decomposition is what makes tuning possible — you can't fix "it feels slow"; you can fix "tts first-chunk p95 is 1.4 s".
  • RTF (real-time factor) = processing time ÷ audio duration, the speech world's throughput unit. RTF 0.08 (our whisper measurement) means 1 CPU core transcribes ~12 concurrent real-time streams, ignoring overheads. Capacity planning starts here.
  • Pipeline, don't accelerate. The cheapest big win in this repo wasn't a faster model — it was sentence-streaming TTS (time-to-first-audio ≈ sentence 1 instead of the whole reply) and continuing to run VAD during ASR/TTS. Overlap hides latency for free.
  • Quantization: whisper here runs int8 — 4× smaller, ~2-4× faster on CPU, negligible WER change. The same knob exists for every engine (ONNX quantization for Silero/Kokoro). Rule of thumb: int8 weight-only is nearly free; going lower needs evals.

5.4Concurrency architecture

asyncio event loop ─ owns: sockets, VAD (<1 ms), state machine never blocks │ asyncio.to_thread worker threads ─ own: ASR + TTS (blocking, CPU-heavy) │ (in bigger deployments this seam becomes a network hop) GPU worker pool ─ dynamic batching, e.g. Triton / Ray Serve / vLLM-style

Three levels of the same idea — keep the I/O plane responsive, put compute elsewhere:

  1. This repo: threads. Fine for a handful of sessions per process; PyTorch/CTranslate2 release the GIL inside kernels so threads genuinely parallelize.
  2. One box, many sessions: a bounded worker pool + queue. Bounded matters: under overload you want queuing (graceful latency degradation) not thrashing.
  3. Fleet: models move behind RPC. The pipeline server becomes a lightweight session host; ASR/TTS become stateless services with dynamic batching — the server collects requests for a few ms and runs them as one batch, because GPUs are throughput machines: batch 8 costs barely more than batch 1. This is Triton's / vLLM's whole reason to exist, and why commercial STT APIs are priced per-minute so cheaply.
Why our engine interfaces survive all three levels transcribe(audio) → Transcript doesn't say whether the work happens in a thread, another process, or another datacenter. That seam — cut here for testing — is exactly where the network goes later. Design interfaces for level 3 even when shipping level 1.

5.5Failure behavior

  • A failed turn must not kill the session — the orchestrator catches per-turn exceptions, emits an error event, returns to LISTENING. The user hears "nothing happened", retries, and the metrics counter increments.
  • Cancellation is a feature (barge-in), so all turn work lives in one cancellable task — cleanup is structural, not ad hoc.
  • Bound everything: max utterance length (30 s), min utterance (250 ms), bounded metric windows. Unbounded buffers are how "it ran fine for a week" becomes an OOM page at 3 a.m.
  • Backpressure (not implemented here): if a client streams faster than real-time or workers saturate, production servers shed load explicitly (reject new sessions at a queue-depth threshold) rather than letting latency creep for everyone.

5.7Telephony notes (the other half of the real world)

Voice agents deployed to phone lines meet a harsher world than a browser mic:

  • 8 kHz, G.711 μ-law — half our bandwidth, a compressive 8-bit codec. Models trained on 16 kHz clean audio degrade badly; production either uses telephony-trained models or accepts the hit. (This is why ASR vendors advertise "phone_call" models separately.)
  • Media streams arrive as RTP or vendor WebSocket streams (e.g. Twilio/Plivo media streams look remarkably like our protocol: base64 PCM frames + JSON control messages — the architecture you just built maps 1:1).
  • No browser AEC — echo cancellation, comfort noise, DTMF detection, and jitter buffers become your problem.
  • Endpointing expectations differ — callers tolerate ~200 ms less silence than app users; IVR-replacement agents tune end_silence_ms per prompt type.

5.8Honest list: what this repo simplifies

  • No auth/TLS/rate limiting on the WebSocket; no reconnection or session resumption.
  • Raw PCM instead of Opus/μ-law; localhost-scale bandwidth assumptions.
  • Fixed-timeout endpointing (no semantic turn detection); browser-provided AEC only.
  • Utterance-based ASR (no streaming partials); echo responder instead of an LLM (the seam is Responder — one method to swap in a streaming LLM).
  • Single process, thread-level concurrency; no autoscaling, batching service, or model registry.

Each is an extension, not a rewrite: the state machine, the engine seams, and the metrics decomposition are the parts that survive contact with production — and they're the parts this repo builds fully.
