Pipeline Architecture

The layer research papers skip: how audio, models, and a user who interrupts you mid-sentence become one real-time system. Code: src/pipeline/, server/app.py, client/.

← contents · the crux

1.1Why a pipeline at all?

Imagine you have a perfect speech recognizer. Zero errors, instant. Now build a voice assistant with it.

You immediately hit questions the recognizer cannot answer:

  • The microphone is always on. What do you even feed it? The last second? Everything since the app started?
  • The user pauses mid-sentence to think. Do you answer now, or wait? If you answer, you have interrupted them. If you wait, how long — and what if they were actually finished?
  • The user starts talking while your agent is still speaking. Does the agent stop? Can it even hear them while it talks?

None of those are recognition problems. A perfect ASR model leaves every one of them unsolved — and they are what people mean when they say an assistant "feels" good or bad. A voice agent is not an ASR model; it is a conversation loop with hard real-time constraints, and the product-defining question is not "what did they say?" but "when do I get to answer, and how fast?"

Audio arrives forever, 16,000 samples per second, and never stops to let you think. That forces a decomposition — each stage answering exactly one question, at a very different cost:

StageQuestion it answersRunsCost
VADIs this 10–32 ms window speech?every window, always<1 ms — must be nearly free
EndpointerHas the user finished their turn?every window, alwaysfree (pure logic)
ASRWhat words were in that turn?once per turn100s of ms of CPU/GPU
ResponderWhat should I say back?once per turnecho here; the LLM in real agents
TTSHow does the reply sound?once per reply sentence100s of ms per sentence
OrchestratorWho runs when, and who gets cancelled?alwaysthe hard part

Read the cost column top to bottom. It spans five orders of magnitude, and that gradient is the architecture: the expensive stages are gated by the cheap ones. A free always-on detector decides when to wake the costly models. That is the economic shape of every production voice system, and it is why VAD models are 2 MB and not 2 GB — a VAD that cost as much as the ASR would defeat its own purpose.

Where we're going. The three questions above map onto the rest of this chapter: what to feed the model becomes the wire protocol (§1.2); when to answer becomes the state machine (§1.3); and "can it hear me while it talks" turns out to dictate the entire threading model (§1.4) — the least obvious and most important consequence in the whole design.

1.2The wire protocol

One WebSocket per session (server/app.py). Two frame types each way — this mirrors what commercial realtime voice APIs (OpenAI Realtime, Deepgram, telephony media streams) do:

client ──▶ server binary: 16-bit LE PCM, 16 kHz mono, ~32 ms per frame server ──▶ client binary: TTS PCM (sample rate announced in tts_start) text: JSON events ready ─ state ─ speech_start ─ speech_end ─ transcript ─ reply ─ tts_start ─ tts_sentence ─ reply_done ─ interrupted ─ error

Why raw PCM and not a codec?

16 kHz × 16-bit mono = 32 kB/s upstream. Trivially affordable on localhost or LAN and dead simple to debug. Production over the public internet uses Opus (~24 kbps) or, in telephony, 8 kHz G.711 μ-law. The decision that matters is deeper: the sample format is a contract — every stage in this repo assumes float32 mono 16 kHz, converted exactly once at the edge (src/pipeline/audio.py, 15 lines, deliberately boring). Format bugs are the classic source of "the model works in the notebook but garbage live".

Why 16 kHz everywhere?

Human speech content lives below ~8 kHz; Nyquist says 16 kHz sampling captures it. Whisper, Silero, and virtually all ASR are trained at 16 kHz. The browser mic runs at 48 kHz, so the client resamples (linear interpolation in client/index.html) before sending — 3× less bandwidth and the server never resamples.

1.3The session state machine

src/pipeline/orchestrator.py — one instance per connected user. All conversation policy lives here and nowhere else:

speech confirmed (start_trigger_ms sustained) ┌────────────┐ ─────────────────────────────▶ ┌───────────────┐ │ LISTENING │ │ USER_SPEAKING │ └────────────┘ ◀──── too short: discard ───── └───────────────┘ ▲ │ endpoint fires │ reply finished ▼ (end_silence_ms) ┌────────────┐ transcript + reply ┌───────────────┐ │ SPEAKING │ ◀──────────────────────────── │ THINKING │ └────────────┘ └───────────────┘ │ └──── user talks over the agent ──▶ BARGE-IN: cancel reply task, tell client to flush audio, jump to USER_SPEAKING

Note what's absent: no "waiting for ASR to finish before listening again". VAD and the endpointer keep consuming mic audio in every state. That single property is what makes barge-in possible.

1.4Barge-in dictates the threading model

The most consequential design constraint in the whole system. Users interrupt — a voice agent that can't be interrupted feels like a 2005 IVR menu. For the agent to hear you while it's speaking:

  • The WebSocket receive loop must never be blocked → ASR and TTS run in worker threads (asyncio.to_thread), never on the event loop. VAD is <1 ms so it runs inline.
  • The reply is an asyncio task the orchestrator holds a handle to — barge-in is literally self._reply_task.cancel().
  • TTS synthesizes sentence by sentence (a generator), so cancellation wastes at most one sentence of compute and playback can start after the first sentence, not the whole paragraph.
  • The client keeps its own playback queue, so the server must send interrupted and the client must flush queued audio — otherwise the agent "keeps talking" out of the buffer even though the server stopped. Distributed-state lesson in miniature: cancelling the producer doesn't empty the consumer's buffer.
The classic bug this prevents Run ASR synchronously on the event loop and everything seems fine in testing — until you talk during a reply and nothing happens: the loop was busy in a 400 ms transcribe call, mic frames queued up unread, and "barge-in" arrives seconds late. Blocking the loop doesn't fail loudly; it fails as deafness.

Echo: why the agent doesn't barge-in on itself

The speaker plays the agent's voice; the mic hears it; the VAD says "speech!" — infinite self-interruption. We rely on the browser's built-in acoustic echo cancellation (echoCancellation: true in getUserMedia), which subtracts what the page is playing from what the mic captures. Speakerphone products (and anything telephony-side) need real AEC (e.g. WebRTC's or Speex's) — it is its own deep DSP field.

1.5The latency budget

The product metric: silence between you finishing and the agent starting to speak ("turnaround" in /metrics). It decomposes exactly:

ComponentThis repo (measured)Production targetThe dial
Endpoint wait (silence to confirm turn end)700 ms (config)300–800 msend_silence_ms — the biggest, dumbest term
ASRscratch: ~50 ms · whisper base.en int8: ~320 ms (RTF 0.08)100–300 msmodel size, quantization, GPU
Responder~0 (echo)300–1500 ms (LLM TTFT)streaming tokens, sentence-split early
TTS first chunkkokoro: ~1100 ms first sentence · scratch: varies100–300 msstreaming synthesis, chunked vocoding
Total turnaround≈ 1–2 s< 800 ms feels natural

Two non-obvious lessons:

  • The endpointer's fixed silence timeout is usually the largest term. That's why the frontier moved to semantic turn detection: a model that reads the partial transcript ("…and my account number is" → clearly not done) and adapts the wait. LiveKit and pipecat ship such models; the fixed timeout remains the baseline.
  • Pipelining beats speeding up stages. Kokoro takes ~1.1 s for sentence one — but if the reply has four sentences, sentences 2–4 synthesize while 1 plays, so the user never waits again. Same trick applies LLM→TTS: stream tokens, cut at the first sentence boundary, start TTS immediately.

1.6What's shared vs per-session

Loaded once per process

ASR and TTS engines — hundreds of MB of immutable weights, seconds to load. Shared by all sessions. Loading per request is the canonical serving mistake (it turns a 300 ms transcription into a 5 s one).

Created per session

VAD engine (it carries RNN/context state across windows), the endpointer (turn state), the orchestrator (conversation state). Sharing state between users is the other canonical serving mistake.

The rule generalizes: weights are shared, state is not. The /healthz endpoint returns 503 until models are loaded so a load balancer never routes to a replica still downloading weights.

1.7Engine swapping

Every stage is a small structural interface (src/pipeline/engines.py): VAD = push(samples) → [prob per window], ASR = transcribe(audio) → Transcript, TTS = synthesize(text) → iterator of chunks. The orchestrator can't tell your 55k-param VADNet from Silero. Three payoffs:

  • Learning: A/B your models against production ones on identical audio.
  • Testing: the entire conversation policy (including barge-in) is unit-tested with fakes in milliseconds — tests/test_orchestrator.py, no model downloads.
  • Production reality: teams swap ASR vendors, self-hosted vs API, per language or per cost tier. The seam you cut for tests is the seam you'll need in prod.
What production adds on top of this exact design Auth & rate limiting on the socket · Opus/μ-law codecs · reconnection with session resumption · semantic turn detection · real AEC · word-level streaming partials from RNN-T ASR · autoscaling pools of GPU model workers behind a queue (the per-process engines here become a gRPC call) · call recording & compliance. None of it changes the state machine you just read.
