01The Production System

The original challenge: thousands of users stream audio over WebSockets; you must run VAD → ASR and stream text back, at low latency, without the gateway freezing or the GPU workers running out of memory.

The golden rule: the event loop must never run a blocking/CPU-heavy call. The gateway only moves bytes; all inference happens in separate worker processes. A thread won't save you — Python's GIL means CPU work in a thread still stalls the loop.

1 · Connection Management & Concurrency

QuestionChoiceWhy
WebSocket frameworkFastAPI + Uvicorn (ASGI / asyncio) WebSockets are I/O-bound; an async event loop holds thousands of idle connections cheaply (one coroutine each, not one thread each).
Keep ML off the loopSeparate worker processes Inference is CPU/GPU-bound. Run it in its own process; gateway communicates via a queue and awaits results.
Scale beyond one coreMultiple gateway workers + worker pool Uvicorn workers for the gateway; an autoscaled pool of GPU workers behind the queue.

2 · Worker Architecture & Data Flow

MechanismWhen to useVerdict
asyncio.Queue / multiprocessing.Queue Single node, prototypeStart here. Zero infra.
Redis StreamsMulti-process / few nodes, low latency Default pick — ephemeral data, consumer groups, visible queue depth for backpressure.
KafkaMassive scale, durability/replay Overkill & adds latency for ephemeral live audio. Name it, don't pick it.
RayPython-native distributed actors + GPU scheduling Great if already Ray-native.
Why VAD before ASR: VAD is cheap (CPU, ~1 ms/frame) and filters out silence/pauses, which dominate real conversations. Gating ASR behind VAD can cut expensive GPU work by 50–80%. ASR workers then batch many users' speech segments into one GPU forward pass.

3 · Backpressure & OOM Mitigation

Bounded everything

  • Inbound queue has a maxsize — never unbounded (that's the road to OOM).
  • When full: drop the oldest audio (a 5s-old chunk is worthless for live transcription).
  • Or stop reading the socket → TCP flow control slows the sender naturally.

Shed & scale

  • Load-shed at the door: reject new sessions (503 / close WS) past a global queue-depth threshold.
  • Autoscale GPU workers on observed queue depth.
  • Dynamic batching with max batch size + max wait → caps memory per step.
  • Cap concurrent sessions per worker; monitor VRAM/RSS and shed before the limit.
One-line summary: Bounded everything, drop stale audio, shed load at the door, scale workers on queue depth. Latency over completeness for live audio.

02Audio → Features (shared front-end)

Both VAD and ASR consume the same input: a log-mel spectrogram. A raw waveform is hard to learn from; the spectrogram exposes which frequencies have energy over time, warped to match human hearing.

→

Framing + Hann
25ms windows overlap by 15ms; Hann tapering kills spectral leakage at frame edges.

Linear <1kHz, log above — we resolve low frequencies far better than high.
log compression
Squashes audio's huge dynamic range; matches roughly-logarithmic loudness perception.

Frame rate = 1000/hop_ms = 100 frames/second. This is the time resolution the models operate on.

03VAD Architecture — "is this frame speech?"

A lightweight frame-level binary classifier. It runs first as a cheap gate so expensive ASR only sees actual speech.

Model (frame-level conv classifier)

input log-mel (B, T, 80) → transpose → (B, 80, T) → Conv1d(80→64, k=5, pad=2) → BatchNorm → ReLU → Conv1d(64→64, k=5, pad=2) → BatchNorm → ReLU → Conv1d(64→64, k=5, pad=2) → BatchNorm → ReLU → Conv1d(64→1, k=1) # per-frame logit output P(speech) per frame → (B, T)
Why conv-over-time? Speech has temporal continuity — a frame is far more likely to be speech if its neighbors are. Convolutions give each output frame a window of context (its receptive field ≈ 13 frames here), the single most useful prior for VAD. → src/vad/model.py

Training

  • loss masked Binary Cross-Entropy (ignore padded frames)
  • labels per-frame 0/1 from synthetic speech vs noise/silence
  • result ~100% frame accuracy on held-out audio
→ src/vad/data.py · scripts/01_train_vad.py

Streaming inference

  • Context buffer: keep recent frames so each new frame gets training-like context.
  • Look-ahead = sharper boundaries but more latency (the core streaming trade-off).
  • Hysteresis gate: enter speech above 0.6, leave below 0.4, with min-duration debouncing.
→ src/vad/stream.py · scripts/02_vad_stream.py

04ASR Architecture — CTC speech recognition

Maps audio → text at the character level. The hard part is alignment: hundreds of audio frames, only a handful of characters, and no per-frame labels. CTC solves it.

The alignment problem & the blank

The network emits one symbol per frame over {characters + blank}. A deterministic collapse turns that frame-string into text:

1) merge repeats: "c c a a a t" → "c a t" 2) drop blanks: "c _ a _ t" → "c a t" (_ = blank) blank separates true repeats: "h e l l o" → "h e l o" ✗ (the two l's merge!) "h e l _ l o" → "h e l l o" ✓ (blank keeps them apart)

CTC training sums the probability of every frame-path that collapses to the target, so the model discovers its own alignment — you never label which frame is which letter.

Model (conv front-end + BiGRU encoder)

input log-mel (B, T, 80) → Conv1d(80→H, k=5, s=1) → BN → ReLU → Conv1d(H→H, k=5, s=2) → BN → ReLU # ×2 time downsample → BiGRU(H → H, 2 layers, bidirectional) # context both directions → Linear(2H → vocab) # 27 chars + blank → log_softmax output (B, T', vocab) → CTCLoss / decoders
Why this shape: conv learns local time-frequency patterns and halves the frame rate (adjacent frames are redundant); the bidirectional GRU mixes context across the whole utterance so each label can depend on what comes before and after. → src/asr/model.py

Decoding

  • Greedy: argmax per frame → collapse. Fast; commits to one alignment.
  • Prefix beam search: sums probability over paths; tracks blank vs non-blank endings to handle repeats. Better on noisy/real audio.
  • Production adds a language model fused into the beam.
→ src/asr/decode.py

Results

  • Synthetic data: 0% character error rate (incl. double letters).
  • Real LibriSpeech (seen): 0% CER — transcribes real speech.
  • Real (held-out, tiny subset): ~67% CER — the data-hunger gap.
→ scripts/04_train_asr.py · scripts/05_train_asr_libri.py

05Putting It All Together

How the models you built slot into the production system.

→
ASR (CTC)batched on GPU
→

Latency lever
VAD look-ahead & ASR batch-wait both trade latency for quality/throughput.
Cost lever
VAD gating + dynamic batching cut GPU spend dramatically.
Stability lever
Bounded queues + load-shedding keep the box alive under spikes.
For true low-latency streaming ASR (instead of full-utterance CTC), the production architecture of choice is the RNN-Transducer (RNN-T) — it emits text as audio arrives. That's the natural next model to build, and it ties directly back to this system-design problem.
